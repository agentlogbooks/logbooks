# Ideation Skill — Usability Stress Test

## TL;DR

- **Axis 1 (start with smaller steps):** the no-signal default is a ~5-minute, 20-idea, framed, compare-report pipeline, and three gates stack ahead of any value — plan approval (t≈22), a frameless `frame.discover` that emits no card (t≈22→70), and a framing checkpoint judged against a blank board (t≈70–101).
- **Axis 2 (record first straight ideas immediately):** the flow never asks for the user's own ideas; the sub-second write path (`add-ideas-batch`) exists but is never used before the framing machinery, so user thoughts go unrecorded while the wall sits empty.
- **Axis 3 (better, more dynamic visualisation):** once ideas exist the board goes inert — cards never reorder, score is an inert corner number, the rank-1 idea sits mid-grid, and 80 cards become one undifferentiated yellow scroll.
- **Sharpest fact:** the first concrete idea card lands at **t≈156s (~2.6 min)** — behind **2 user-interaction blocks** and **2 subagent round-trips** (observations.md §A). The wall, the skill's best feature, opens on "Waiting for ideas…" and stays empty through the session's longest dead stretch.
- **A working fix for axis 3 already exists:** `stress-test/ideation/view.dynamic.html` is a verified drop-in on the same SSE contract — FLIP reorder-on-score, score→heat bar, rank badges + winners band, cut→compost tray, live activity line. A/B screenshots prove the gap.
- **Notable:** cross-session persistence is silently broken — the CLI reads `.logbooks/ideation/` while every committed dogfood logbook lives at `.ideation/` (observations.md §C), so `list-topics` returns `[]` and every prior topic is invisible after the path refactor shipped with no migration.
- **logbook-creator:** ideation is logbook-creator's best worked example, but the creator flow demotes the "Visualize" projection to an optional Step-4 aside — so the wall (and its static limitations) emerged as bespoke infra rather than a designed output.

## How this was stress-tested

Evidence was gathered by running the real `ideation_db.py` CLI and replaying a faithful `starter` session through both walls with the harness in `stress-test/ideation/` (`wall_replay.py` + `scenarios/`). The timeline scenario (`scenarios/timeline.jsonl`) reproduces the lightweight default with conservative wall-clock-shaped gaps for subagent round-trips and human reads; peak-load and churn scenarios (`scenarios/state_80.jsonl`, `state_churn.jsonl`, `state_scored.jsonl`) drive both `live/view.html` and the `view.dynamic.html` prototype to capture A/B screenshots under `screenshots/`. Findings come from a multi-lens audit (the three priority axes, first-time and power personas, general UX, persistence, logbook-creator) and were re-run through adversarial verification against the schema (`ideation_db.py`) and the wall handlers (`live/view.html`) to keep every recommendation feasible in-ecosystem. Ground truth is `stress-test/ideation/observations.md`.

## Axis 1 — Start with smaller steps

### 1.1 Three gates stack ahead of the first idea, and the first round-trip produces zero cards (severity: high)

The default first experience front-loads its heaviest reads onto its most fragile moment. Plan approval is a full-roadmap gate at t≈22 (USER BLOCK 1; SKILL.md Step 4). The first operator, `frame.discover`, emits **no card by design** ("frame.* | none (frames are not cards)", SKILL.md per-operator emit table) — so the entire first round-trip (t≈22→70, the slowest, most front-loaded part) leaves the wall empty (`screenshots/current_state_empty.png`: lightbulb, "Waiting for ideas…", Ideas: 0). The user's first signal of progress is a framing checkpoint with the idea count still at zero (`screenshots/current_state_framing.png`). These gates plus two round-trips are what push first value to t≈156s.

**Recommendation (in-ecosystem):** populate the wall during the dead stretch with the existing event path. Between `session_started` (Step 2) and the planner spawn (Step 3), emit `idea_generated` directly via `live/emit.py` for the user's raw intent — the wall renders from the SSE payload alone (the `idea_generated` handler reads only id/title/description/kind/tag/status and never touches SQLite), so a card lands in under a second with no frame and no FK obstacle. In parallel with the planner subagent, optionally spawn one `generate.fresh hint=<intent> count=3` op (SKILL.md already supports parallel Agent spawns in Step 5C) with its own `op-start`/`op-finalize` row, scoped to fresh topics only; its prompt's documented fallback to "broadest possible spread" handles the frameless warm-up. The user reads the plan while real cards appear. Extends the prior idea **#6** cheap-warm-up spirit (note #6 *discards* its seeds; this keeps the warm-up cards on the wall).

### 1.2 The framing checkpoint is a blank-page judgment placed before any ideas exist (severity: high)

`starter`'s single user interruption (starter.md Notes: "The framing checkpoint is the only user interruption") asks the user to confirm an abstract frame — root causes plus HMW questions — before they have seen a single idea (USER BLOCK 2, t≈70–101, board still ZERO ideas; `screenshots/current_state_framing.png`). High-commitment judgment at the moment the user has the least to anchor on.

**Recommendation (in-ecosystem):** split generation so a few concrete cards precede the judgment. In starter.md, make step 2 a small pre-checkpoint batch (`generate.seed persona=innovator count=5`, using the existing `count=` param), move the framing checkpoint to after it, then run the remaining ~15 seeds. Turn the checkpoint from a gate into a sharpener by adding a low-commitment third option to the existing framing AskUserQuestion: "Looks right — generate more" / "Sharpen the frame" / "Skip — just generate"; on "Sharpen" patch the active frame before the remaining `generate.seed` steps. All existing verbs and the existing `checkpoint_reached`/`checkpoint_resolved` emits. Extends prior ideas **#6** (pick direction from actual evidence, not a blank-page HMW) and **#8** (user leads, agent interrupts).

### 1.3 The no-signal default is too big (severity: medium)

When the user's intent carries no signal, the planner defaults to `starter` — frame + 20 ideas + checkpoint + compare report, "~5 min" (SKILL.md line 553) — chosen precisely when the system knows least about what the user wants. The true zero-signal move should be the smallest one.

**Recommendation (in-ecosystem):** add `playbooks/spark.md` = a lean `frame.discover` (still mandatory — the schema requires a frame, see §Notable / Axis 2.3) + `generate.seed persona=innovator count=6` (default is 12, lowerable) + no compare report, and add a planner rule exempting default-selected lightweight playbooks from auto-checkpoint insertion (SKILL.md already suppresses auto-checkpoints for `--no-checkpoints` and explicit-playbook intents — extend that to scoped lightweight defaults so the framing checkpoint does not silently survive). Make `starter` the explicit "fuller first pass," and keep Step 6 follow-up routing `spark → starter` as "give me the full pass." Honest ceiling: sub-second first-idea is impossible in-ecosystem (the `frame.discover` round-trip stays), but 20→6 ideas with no checkpoint and no report is a genuine reduction. Extends prior idea **#4** (heavy infra becomes opt-in).

## Axis 2 — Record first straight ideas immediately

### 2.1 First idea lands ~2.6 min in; the user's own ideas are never asked for (severity: high)

A first-time user who types `ideation cafe: grow afternoon revenue` arrives with a concrete intent, but the skill jumps straight to agent-led framing and parallel generation. There is no capture step between "user has intent" and "planner runs" (SKILL.md Step 3 spawns the planner immediately after wall-start). The wall opens on "Waiting for ideas…" and produces nothing for ~2.6 minutes (observations.md §A; `screenshots/current_state_empty.png`, `current_state_framing.png`) — empty exactly when the user's own thoughts are hottest, and those thoughts go unrecorded so the agent may regenerate or miss them.

**Recommendation (in-ecosystem):** the headline fix is the same instant-emit path as 1.1 — at Step 2, right after `session_started`, emit `idea_generated` via `live/emit.py` for the user's raw intent and any half-formed ideas in the invocation. The board populates in under a second with zero FK/frame obstacle because the handler renders from the SSE payload alone. For durability, backfill the rows once `frame.discover` has created the active frame (see 2.3). Extends prior idea **#8** (user leads, agent interrupts).

### 2.2 No place to drop an idea mid-session (severity: medium)

Ideas arrive while reading generated cards ("oh, that reminds me of X"), but Steps 5A–5E are entirely operator/checkpoint driven; the only user inputs during execution are checkpoint confirmations, and none accept a new raw idea (prior idea **#12** "input buffer for intent" names exactly this gap).

**Recommendation (in-ecosystem):** add an "I have an idea to add (Other)" branch to existing checkpoint AskUserQuestion calls (Step 5A) — the framing checkpoint already exposes an "(Other)" branch, so this reuses existing machinery with no new event type. On that branch, write the text via `add-ideas-batch` reusing the active frame (`_insert_idea` resolves a `None` `frame_id_at_birth` to the active frame, and every checkpoint fires after `frame.discover`, so a frame always exists), and satisfy the NOT-NULL `origin_operator_run_id` with an `op-start --operator user.capture` label (the op-start INSERT does not validate the operator name). Emit the standard `idea_generated` event so the captured card lands on the wall. Scope honestly: this delivers capture at pause points (first checkpoint ≈ t≈70s), not the cold-start capture axis-2 names — pair it with the cold-start instant-emit path in 2.1 to cover both. Extends prior idea **#12**.

### 2.3 The schema hard-blocks recording a raw idea before framing — and the workaround must be documented (severity: high)

observations.md §A frames `add-idea` as "a direct path to write a raw idea in well under a second," but a *durable* row pre-frame is blocked: `ideas.frame_id_at_birth` and `ideas.origin_operator_run_id` are both NOT NULL FKs, and `add-idea` hard-exits with "no active frame — run frame.discover before generating ideas." There is a mandatory three-call bootstrap the skill never documents.

**Recommendation (in-ecosystem, verified to run in ~0.45s):** document one reusable capture fragment in SKILL.md, used by both the cold-start backfill (2.1) and `spark.md` (1.3):
1. `OP=$(ideation_db.py op-start <slug> --run-id $RUN_ID --operator user.capture --cohort-ids-json '[]')`
2. `ideation_db.py add-frame <slug> --problem-statement '<raw intent>' --root-causes-json '["tbd"]' --hmw-questions-json '["tbd"]' --operator-run-id $OP` — **note: `add-frame` rejects empty arrays, so the placeholders must be non-empty (`["tbd"]`, not `[]`)**. A later `frame.discover` automatically supersedes this placeholder frame (verified: active=0 on v1, active=1 on v2).
3. `ideation_db.py add-ideas-batch <slug> capture.json --origin-operator-run-id $OP`

The cleanest variant avoids the stub entirely: when the user already has ideas, buffer them and write the durable rows via `add-ideas-batch` *after* the framing checkpoint confirms (~t≈101) and before the `generate.seed` subagents spin up — this binds them to the real active frame, with no orphaned `frame_id_at_birth`, and still removes the ~55s generate round-trip for the user's own ideas. The instant-emit path (2.1) covers the <1s wall feedback; this covers durability. Extends prior ideas **#4**/**#6**/**#12** by giving them a concrete working capture primitive.

## Axis 3 — Better, more dynamic visualisation

### 3.1 The populated board never reorders or heat-encodes — promote the prototype (severity: high)

This is the user's third named priority, and the current wall fails it precisely when ideas exist. `view.html` appends cards in arrival order and never moves them; `idea_scored`→`patchCard` updates a number in place with no reflow. The rank-1 idea sits mid-grid as an inert corner number (`screenshots/current_state_scored.png` vs `dynamic_state_scored.png`); at the deep_explore peak of 80 stickies the five winners are invisible (`current_state_80.png` vs `dynamic_state_80.png`); cut cards stay full-size and interleaved (`current_state_churn.png` vs `dynamic_state_churn.png`). The board's only motion (pop-in, pulse, blink) all happens while it is empty.

**Recommendation (in-ecosystem quick win):** promote the already-built prototype to the live wall — `view.dynamic.html` is a verified drop-in on the identical `EventSource('/events')` contract with the same handler key set, zero new event types, vanilla HTML/JS/SSE, no libraries (observations.md §B). Every behavior keys off events the orchestrator already emits: FLIP reorder-on-score and score→heat bar from `idea_scored`, rank badges + winners-first sort from `idea_ranked`, cut→compost tray (inspectable — the tray cards reuse `openModal`, which already renders `stress_note` under "Why it was cut") from `idea_cut`, and a live activity-narration line. Regression-parity is clean: the only differences are a dropped vestigial "hybrid" status label that no handler emits, and nth-child card coloring replaced by kind-tint (a deliberate fix, since nth-child coloring would reshuffle on every FLIP).

### 3.2 Surface kind and tag as a navigation axis (severity: medium)

The wall already receives `kind` (seed/variant/hybrid) and `tag` (BOLD/WILD/SAFE) on every `idea_generated` payload (`scenarios/state_80.jsonl` confirms `kind`/`tag` distributions) but throws both away visually — `view.html` renders kind as an 8px dot and tag not at all, so a user cannot see the shape of the idea space (`current_state_80.png`: all 80 cards read as identical yellow). The cheapest dynamic structure sits unused on the contract.

**Recommendation (in-ecosystem):** all pure render-layer, off the already-captured payload (`ideas[p.id] = {...p}`). (a) A small colored corner chip per card (BOLD/WILD/SAFE → three accents) so the space's shape is legible at a glance; (b) a tag histogram in the existing stats bar (bold/wild/safe counts alongside Ideas/Active/Kept/Cut) so the board narrates its own diversity as cards land; (c) a vanilla-JS filter bar — clickable kind/tag chips plus a text input that toggles a `.hidden { display:none }` class in a small `applyFilters()` pass invoked from the existing handlers. Note there is no existing user-facing sort toggle (the `#sortMode` in the prototype is a passive status label), so a reflow-mode switch needs a small new vanilla-JS button. Extends prior idea **#14** (docent mode) by making the populated wall self-navigable, and the **#18** compost-heap metadata thinking.

### 3.3 Peak-load (80 cards) needs zone structure and a coalesced reflow (severity: medium)

The prototype's score-sort rescues the top of an 80-card board, but the long tail stays a flat undifferentiated grid with no section breaks (`dynamic_state_80.png`), and — honestly — the prototype's full-board FLIP does not scale: `reflow()` calls `getBoundingClientRect()` over every live card and re-appends the full ordered list on each of the four idea/score/rank/cut handlers (measured: 171 `reflow()` invocations against `state_80.jsonl`, the later ones repositioning up to 80 cards in a forced synchronous layout). So promoting the prototype is the high-value quick win, but the 80-card wall needs this follow-on.

**Recommendation (in-ecosystem):** (1) give ranked/kept winners a fixed always-visible region — reuse the already-present-but-unused `.section-label.winners` scaffolding to render ranked cards into a pinned band above the grid (getBoundingClientRect inversion works across containers, so cards animate from grid into band); (2) make `reflow()`/`orderedIds()` zone-aware — full cards above a running-median threshold, a collapse-on-click "lower-scored (N)" chip band below it (mirroring the existing compost-tray toggle); (3) coalesce reflow with a `requestAnimationFrame` guard so a burst of `idea_scored` events from one parallel score op collapses into a single layout pass (the file already uses rAF, so the pattern is idiomatic). All vanilla, same SSE contract.

### Additional dynamic behaviors (lower severity, additive)

- **Lineage and tension edges (medium):** which idea descends from which exists in the data (`lineage` table, populated by `transform.hybridize`/`evaluate.tension`) but never reaches the wall — `parents` is read in the modal but never drawn on the board. First close the data gap (extend the per-row emit loop to `SELECT parent_idea_id FROM lineage WHERE child_idea_id=?` and include `parents:[...]` in the `idea_generated` payload), then add a vanilla-SVG overlay recomputed on each `reflow()` pass from the rects the FLIP code already gathers; emit an additive `idea_tension {a,b}` event from `evaluate.tension` for faint dashed edges. Ship behind the populated-board state (deep_explore, not starter).
- **Aliveness pulse (low):** port the prototype's header activity line + `setActivity()`, newest-card glow, and per-stat `.bump` so scores do not land silently during the long evaluate phase. For the heat-bar fill, update the existing `.heat` element's `style.width`/`background` in place rather than rebuilding the card's `innerHTML` (which destroys the node and defeats its own `transition: width .5s`). Additive polish on top of 3.1.
- **Provenance marker for user ideas (low):** once a record-first capture path exists, route user ideas through `op-start --operator user.capture`, add one `origin:'user'` field to the `idea_generated` payload and emit loop, and have `renderCard` print "YOURS" in the existing `.status-tag` span when `origin==='user'` — so the agent's later transforms do not silently "improve" a user-authored idea with no marker. One payload-field addition, no new event type, no DB-schema change.

## Notable finding — cross-session persistence is fragile (severity: high)

This is notable by *position*, not by impact — the impact is severe. `ideation_db.py` resolves topics to `<git-root>/.logbooks/ideation/<slug>/` (`IDEATION_DIR = ".logbooks/ideation"`), but the repo's actual committed dogfood logbooks live at `.ideation/<slug>/` — 68 git-tracked files across `grow-afternoon-revenue`, `ideation-skill-improvements`, `code-review-skill` (observations.md §C). The result: `list-topics` returns `[]`, `show-state ideation-skill-improvements` returns nothing — every prior topic is invisible to the current CLI. Git history shows the path was refactored (`538accd` "use hidden ./.logbooks/", `dbc4179` "consolidate plugin storage") with **no migration**, and it shipped. The skill's headline promise is "ideas persist across sessions; follow-up prompts resume where the last one ended" — a returning user who upgrades past that refactor silently loses access to every topic and is told "topic doesn't exist — create it?", re-running brainstorms they already paid for. Worse, `live/emit.py` and `live/serve.py` independently hardcode `.logbooks/ideation/`, so the wall path and CLI path can diverge with no shared constant.

**In-ecosystem fix:** (1) a one-time migration that moves/symlinks any legacy `.ideation/<slug>/` into `.logbooks/ideation/<slug>/` on first run (or a `list-topics` that reads both and offers to migrate); (2) a single shared path constant imported by `ideation_db.py`, `live/emit.py`, and `live/serve.py` so the CLI and wall can never diverge again. This is also a direct violation of logbook-creator's own "Logbook address" rule — see Conclusions.

## Other UX findings

- **Winners are visible but un-actionable (medium):** the integer idea ID needed for every Step-6 follow-up (`develop idea N`, `hybridize N and M`) is the one field the wall never shows — not on the card, not in the modal (`current_state_scored.png`). A user looking at the gold-ringed #1 has no way to learn which `idea_id` to type. Quick fix: render `#<idea.id>` as a small corner label in `renderCard` and an ID cell in the modal `.m-meta` row — pure template change, ID is already in the payload. (A copy-ready command snippet is a separate, larger change: it needs a `slug` field added to the `session_started` payload, since the wall only carries the display topic, not the CLI slug.)
- **deep_explore forces 5 blocking checkpoints with no deferred-review path (medium):** a power user who walks away returns to a session frozen at checkpoint 1 of 5 (deep_explore.md: framing, taste, criteria_lock, before_validation, before_decide). Scope the existing all-or-nothing `--no-checkpoints` into a named opt-out covering the three deferrable gates (`criteria_lock`, `before_validation`, `before_decide`) while keeping framing always blocking (taste is already auto-delegated to `evaluate.taste_check` — precedent that the skill handles checkpoints non-uniformly). Pair it with a small `view.html` change so an auto-approved checkpoint converts its pause card into a persistent "auto-approved: criteria_lock" log card instead of being removed, leaving a reviewable trail. Extends prior idea **#5**.

## Conclusions about logbook-creator

Ideation is logbook-creator's strongest worked example, and stress-testing it exposes four conclusions about the creator itself:

- **The worked example understates the reality.** `concept.md`'s "Ideation logbook" example is a flat **CSV** (`id, name, description, source_agent, phase, tag, ICE scores`), but the real implementation is a **multi-entity SQLite** logbook (`topic_meta, frames, facts, ideas, lineage, assessments, operator_runs`) plus a JSONL run-trace and the live wall as an export-only visualisation projection (observations.md §D). The concept under-describes what a serious "deep ideation" logbook becomes — the exact gap its own "deep workflows need logbooks" section gestures at.
- **The Visualize/projection step is under-served.** `concept.md` lists "Visualize" as a first-class action and names projection roles (run-trace / export-only / mirror), but the SKILL.md flow demotes projection design to an optional aside in Step 4 with no design questions of its own. The consequence is concrete: the live wall — ideation's best UX feature and the only thing addressing axis 3 — emerged as bespoke infra *outside* the design conversation, which is why the static-board limitations (insertion-order cards, inert score numbers, no sort/heat) are the default a creator session produces today.
- **The trace→view link is missing.** logbook-creator gets the run-trace right (`live-events.jsonl` is exactly the append-only log the concept describes) but never walks the user from "you have a run-trace" to "therefore design the export-only view a human watches." Because that link is absent, ideation's wall consumes the trace yet stays flat.
- **The address-stability rule was violated.** The §C persistence break is a direct violation of `concept.md`'s "Logbook address" rule ("a stable reference that works across sessions… when the user moves this file, update the address here") — the refactor moved the store with no stable, migrated address.

**Concrete creator-flow improvements (pure SKILL.md / template prose, no infra):** (1) add "a chart, board, or dashboard view" to the Step-3C actions targets, and fire a required follow-up whenever the logbook is append-heavy and watched: "When this is populated, how does a human SEE the slice at a glance — what does the winner/strong/cut row look like, and what reorders or encodes as state changes (score→position, status→tray)?"; (2) make "Visualize" a first-class `## Actions` template entry with its own slots — projection role (tie to the Step-4 export-only role), group-by/sort key, and the state-driven encoding (which transitions read as motion: new row, score assigned, status cut/kept); (3) keep Step 4's three roles but add a cross-reference that a Visualize action is realized as an export-only projection paired with its watched run-trace. This makes axis-3 dynamism a *designed* output of the conversation. It does not itself remediate the existing wall — that needs the 3.1 drop-in.

## Recommended next moves

**Quick wins (small, in-ecosystem, high value):**
1. **Promote `view.dynamic.html` → `live/view.html`** — verified drop-in, fixes axis 3's headline (reorder, heat, rank badges, winners band, compost tray) with zero schema/event change.
2. **Emit `idea_generated` at Step 2** for the user's raw intent — populates the wall in <1s, no FK/frame obstacle; serves axes 1 and 2 at once.
3. **Render the idea ID** on the card and in the modal — one template change, makes winners actionable.
4. **Persistence migration + single shared path constant** across `ideation_db.py`/`emit.py`/`serve.py` — stops silent loss of every prior topic.
5. **Kind/tag chips + tag histogram** in the wall — pure render off the existing payload.

**Larger changes:**
6. **`spark.md` + planner default rule** — smallest zero-signal path (6 ideas, no checkpoint, no report), `starter` becomes the explicit fuller pass.
7. **Durable capture bootstrap fragment** (op-start → add-frame with `["tbd"]` placeholders → add-ideas-batch) documented once and reused by cold-start backfill and `spark.md`.
8. **Split-generation framing checkpoint** (a few seeds before judgment, low-commitment "Skip/Sharpen" options).
9. **Peak-load zone reflow** — pinned winners band + collapse tail + rAF-coalesced FLIP (the 80-card follow-on that the prototype drop-in alone does not solve).
10. **Scoped checkpoint opt-out** for deep_explore + persistent auto-approved log cards.
11. **logbook-creator prose edits** — make Visualize/projection a designed step so the next ideation-like skill ships a dynamic populated-state view by default.

# Validation — feed ideas → iterate → visualize

## Verdict
Two-thirds real, and the missing third breaks the whole loop. Today you can iterate on imported ideas perfectly (every operator and cohort query treats them as first-class rows), and the wall is genuinely capable of visualizing them well — but there is no supported flow to *feed* ideas from an external source, and import+iterate via the CLI never reaches the wall on its own. The empirical run confirms all three: a naive `add-idea` on a fresh topic fails with "no active frame" (run.log lines 7-9); a hand-built bootstrap (op-start → add-frame placeholder → add-ideas-batch) lands 8 first-class ideas that iterate cleanly (run.log 11-26, STAGE 2); but after that CLI import+iterate **no `live-events.jsonl` existed** so the wall showed nothing (run.log 96-100), and the good visualization in wall.png only appeared after 9+ `idea_generated` events were emitted **by hand** (run.log 116-119). The journey as written is not something the skill walks a user through end-to-end.

## Stage-by-stage

### FEED — supported: NO
There is no first-class path to bring a user's own ideas into a topic. The Invocation block (SKILL.md lines 22-28) lists only `topic:intent`, `--playbook`, `--no-checkpoints`, `--list-topics`, `--show-state` — none ingest. The planner decision procedure (SKILL.md 117-160) only matches IDs already in the logbook (step 2, 131-134) or falls through to the `starter` playbook (line 140); it never parses pasted idea text. And `starter.md` (steps 19-24) runs `frame.discover` + `generate.seed` ×2 (~20 fresh ideas) — so "ideation new: here are my 8 ideas" generates its own and ignores the user's. No `import`/`ingest`/`user.*` operator exists (operators/ has 26 files; `generate.seed`/`generate.fresh` both *produce* new ideas). The frame-FK is a real wall: `ideation_db.py` `_insert_idea` (616-625) `sys.exit`s "no active frame" when none is active, which both `add-idea` and `add-ideas-batch` hit (run.log 7-9). **Gap:** the only way ideas land today is the out-of-band CLI dance in the run log, whose audit row even records a **fabricated** operator name `user.import` (run.log line 91) with no operator file behind it — proof the skill offers no real flow.

### ITERATE — supported: YES
Once ideas are in, iteration is fully real. Imported rows are `kind=seed, status=active` (run.log 36), and every transform/evaluate/validate/decide operator's `applies_to.kinds` includes `seed` or is empty, so they pass the kind gate the orchestrator enforces (SKILL.md Step 5D). All cohort SQL is provenance-blind — `_query_all_active`, `_query_all_active_capped`, `_query_all_seeds`, `_query_diversity_top` key only on status/kind, never on origin (ideation_db.py ~1248-1322) — so `decide.route cohort=all_active_capped(50)` picks up imported ideas. Empirically: all-active cohort = [1..8] (run.log 47-56), a transform child idea 9 with lineage `relation=refinement_of`→parent 1 (run.log 102-114), assessments scoring ideas 1-3 (composite 78/71/64, run.log 73-81), and a clean op-runs audit trail. The `relation must be one of` error (run.log line 60) was a tester typo (`refine` vs `refinement_of`), corrected at 102-114 — not a defect. **Caveat (non-blocking):** the run log exercised the CLI/data layer; the orchestrator→planner→subagent routing for "develop idea N" is sound-by-construction (imported rows are indistinguishable to the planner) rather than directly observed. Quality is bounded only upstream — under bootstrap the frame is a placeholder, so run `frame.discover`/`frame.reframe` before deep iteration.

### VISUALIZE — supported: PARTIAL
The wall is capable but the import/iterate path is not wired to it. After CLI import+iterate, `live-events.jsonl` does not exist (run.log 98), so the wall shows nothing. The CLI never emits (grep for `emit`/`live-events` in ideation_db.py = zero matches); operators never emit; emits are orchestrator-only (SKILL.md Step 5, per-operator table 646-663). There is no DB rehydrate — `serve.py` reads only `live-events.jsonl` (lines 18-19, 46-58) and never opens `logbook.sqlite`. Even a subsequent orchestrator iteration would surface only the new child as an orphan, because the Step-5 emit loop selects `WHERE origin_operator_run_id=?` (SKILL.md 375-391) — imported ids 1-8 are never re-emitted. **But the wall itself works:** fed 15 hand-emitted events (run.log Stage 3b), wall.png renders a "SELECTED — FINAL RANKING" winners band (#1, #2 cards), score heat ("BELOW 70", score 64), "NOT YET SCORED" cards, the transform child, and stats "Ideas: 9 / Active: 9". **Gap:** the journey's actual payload is 100% invisible until someone hand-emits.

## The minimal fix (in-ecosystem)
One coherent move makes the whole journey real, using only existing CLI verbs + `emit.py` + a planner path — no new infra:

1. **Add a `generate.import` operator** (`operators/generate.import.md`). Because it is prefixed `generate.*`, the orchestrator's Step 5 per-operator emit table **auto-emits `idea_generated` per row**, so the wall populates for free, and `op-start`/`op-finalize` write a real audit row instead of the fabricated `user.import`. It parses the user's pasted ideas and writes them via `add-ideas-batch`, which already supports `frame_id_at_birth` (ideation_db.py 685) and inline parents/relation lineage (688-699) — the substrate is there.
2. **Sequence a frame step first.** Operators must not touch frames except via `frame.*` (SKILL.md 260) and the FK is enforced (ideation_db.py 616-625), so the planner runs a lightweight `frame.discover` (or placeholder frame) before `generate.import` so the FK resolves.
3. **Add a planner branch** (SKILL.md ~131-140): if the intent supplies external idea text ("here are my ideas", "import these", a pasted list), route to `frame.discover` → `generate.import` instead of falling through to `starter`.
4. **Add an invocation form** to the SKILL.md Invocation block, e.g. `ideation <slug>: import these ideas: ...` (or `--import <file-or-list>: <intent>`).

This fixes FEED and the VISUALIZE-for-imports gap in one stroke — imported ideas land as cards on the wall at ingest, and existing follow-up flows (`followup_develop`, `hybridize_pair`, `stress_test_shortlist`, `route`) then iterate with the wall already wired. This is exactly prior improvement-logbook idea #8 ("user leads / record-first") and the axis-2 UX gap.

## Caveats
This is an n=1 journey from a single CLI run — the data layer was exercised directly, but the user-facing orchestrator→planner→subagent routing for ingest and "develop idea N" was validated by construction, not observed end-to-end. The wall's capability (wall.png) was proven with **hand-emitted** events, not events produced by the skill itself; it demonstrates the wall *can* render an imported+iterated topic, not that the current import path *does*.
